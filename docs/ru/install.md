# Установка ноды Nexora

Нода — это плоскость данных: агент без состояния, который терминирует
клиентский трафик и делает то, что велит панель. У него нет ни базы данных, ни
интерфейса управления, ни файла настроек, который стоило бы резервировать —
единственное его состояние — пара сертификатов. Так задумано: потерянная нода
заново регистрируется в панели и возвращается точно такой же, и ничего на ней не
нужно переносить или восстанавливать.

Устанавливать ноду с этой страницы почти никогда не приходится. **Панель ставит
ноды за вас**, и однострочная команда, которую она выдаёт, — поддерживаемый путь.
Здесь сначала подробно разобран он, а затем ручной — для случаев, до которых
панель не дотягивается.

## Требования

- Linux-сервер с systemd. Публикуются amd64, arm64, armv5/v6/v7, 386, s390x и
  riscv64.
- Доступ root.
- Исходящий доступ к панели и TCP-порт **62050**, доступный *со стороны панели*
  по IPv4 или IPv6 — нода слушает оба.
- Порты, на которых будут слушать назначенные этой ноде inbound'ы.

Собственный лицензионный ключ ноде не нужен. Лицензия панели ограничивает,
сколько нод она будет обслуживать.

## Обычная установка

Добавьте ноду в панели и скопируйте показанную команду:

```bash
curl -fsSL https://PANEL/install-node.sh | bash -s -- --panel PANEL --token TOKEN
```

Запустите её от root на новом сервере. Меньше чем за минуту она:

1. Определяет архитектуру и скачивает бинарник ноды **с вашей панели**, а не из
   интернета.
2. Обменивает `TOKEN` на клиентский mTLS-сертификат панели. Токен одноразовый и с
   истечением; панель гасит его этим же запросом, и больше он не сработает.
3. Генерирует собственный серверный сертификат и ключ ноды.
4. Пишет `/opt/nexora-node/config.json` и unit systemd, затем запускает службу.

Панель подключается, запоминает отпечаток сертификата ноды на первом же
соединении и дальше принимает только его — доверие при первом использовании. Нода
со своей стороны принимает только клиентский сертификат панели. Ничто другое в
интернете не сможет заговорить с портом 62050 так, чтобы пройти TLS-рукопожатие.

Что можно добавить к команде:

| Флаг | Действие |
| --- | --- |
| `--listen ADDR` | привязать управляющий API не к `[::]:62050` (IPv6-wildcard, который обслуживает и IPv4) |
| `--binary-url URL` | взять бинарник не с панели |

Если у панели нет подготовленного бинарника для архитектуры этого сервера,
установка падает на шаге 1 с `node binary not provisioned`. Подготовьте его на
хосте **панели** и повторите — не переходите ради этого на ручную установку:

```bash
# на сервере панели
curl -fsSL -o /tmp/node.tar.gz \
  https://github.com/nexora-vpn/node/releases/latest/download/nexora-node-linux-armv7.tar.gz
tar -C /tmp -xzf /tmp/node.tar.gz
install -m 0755 /tmp/nexora-node/nexora-node /var/opt/nexora/bin/nexora-node-linux-armv7
```

## Автоматическая установка

Панель может проделать всё описанное выше сама, по SSH. В окне установки узла —
или внизу диалога добавления узла — перейдите на вкладку **Автоматически (SSH)**,
дайте панели логин к серверу и нажмите **Определить**.

Она сообщит, что это за сервер (дистрибутив, архитектура, есть ли systemd или
Docker) и что на нём уже стоит, а затем покажет план: каким способом развернёт и
на какую версию выйдет. Нажмите **Установить** — вывод придёт в реальном времени.

От команды выше это отличается одним важным свойством: панель **загружает** файлы
сама. Установщик, клиентский сертификат панели и — по умолчанию — сам бинарник
узла идут по SSH-соединению. Серверу не нужен ни маршрут до панели, ни до GitHub,
ни доверие к TLS-сертификату панели. Ничего не скачивается, поэтому и токен
установки здесь не участвует.

Запустите позже ещё раз — обновит на месте, сохранив `config.json` и собственный
сертификат узла, так что закреплённый отпечаток по-прежнему совпадает и ничего
не нужно регистрировать заново.

### Учётные данные

По умолчанию ничего не сохраняется. Пароль используется для одного подключения и
отбрасывается.

Отметьте **Разрешить ключ панели на этом сервере** — панель допишет свой
публичный ключ в `authorized_keys` пользователя и тут же проверит его вторым
подключением. После этого обновления не потребуют пароля вовсе. Это постоянный
доступ ко всему, что может этот пользователь, — отзовите его из меню узла
(**Отозвать ключ панели**) или удалив строку `nexora-panel-…` из
`~/.ssh/authorized_keys` вручную.

Пользователь не обязан быть root. Подойдёт пользователь с sudo: панель повысит
права указанным вами паролем.

Первое подключение закрепляет SSH-ключ хоста — так же, как панель закрепляет
TLS-сертификат узла. Если позже сервер предъявит другой ключ, панель откажется
подключаться и скажет об этом, а не продолжит молча: либо машину заменили, либо
между вами кто-то есть.

### Перенос узла на другой сервер

Используйте **Перенести на другой сервер** в меню узла, а не правку адреса. К
машине, на которой узел работал, привязаны три вещи: закреплённый
TLS-сертификат, SSH-ключ хоста и то, что панель помнит о способе развёртывания.
Перенесённые на новый сервер, первая отвергнет любое подключение, вторая — любой
вход, а третья заставит установщик планировать обновление Docker для хоста, где
Docker может не быть вовсе. Перенос очищает всё три, после чего вы ставите узел
на новый сервер как на новый — потому что он и есть новый.

### Способ развёртывания и версия

Оба подбираются автоматически и оба можно переопределить.

Способ по умолчанию — тот, которым сервер уже работает, так что обновление
никогда не превратит узел из контейнера в сервис или наоборот незаметно. На
чистом сервере берётся systemd, если он есть, иначе Docker. Явный выбор другого
поддерживается: установщик сначала убирает прежнее развёртывание, чтобы они не
делили порт 62050.

Версия по умолчанию — бинарник узла, подготовленный на вашей панели: тот, что
установщик панели скачал рядом с собой. Запросите конкретный релиз — и сервер
скачает его с GitHub; то же происходит автоматически для архитектуры, для
которой на панели ничего не подготовлено (она готовит amd64 и arm64; armv7, 386,
s390x и riscv64 приходят из релиза). Установка в Docker тянет соответствующий
тег образа.

## Файрвол

Порт 62050 говорит по mTLS и отвергает всех, кроме панели, но выставлять его
наружу незачем:

```bash
ufw allow from PANEL_IP to any port 62050 proto tcp
```

Если панель приходит к этой ноде по IPv6, правило должно называть тот адрес, с
которого соединение действительно приходит: правило для v4 не покрывает
соединение по v6:

```bash
ufw allow from 2001:db8::1 to any port 62050 proto tcp
```

Клиентские порты — отдельная история. Это порты назначенных ноде inbound'ов, то
есть они выбираются в панели: открывайте их после назначения шаблона, а не до.

## Нода, доступная по IPv6

Ничего особенного не требуется ни с одной стороны. По умолчанию нода слушает
`[::]:62050`, что на dual-stack хосте принимает и соединения по IPv4 — то есть
одна и та же установка работает, приходит ли панель по v4, по v6 или по обоим. На
хосте, где IPv6 выключен полностью, нода не может привязать этот адрес и сама
откатывается на `0.0.0.0:62050`, что для такого хоста и имелось в виду.

Серверу **только** с адресом IPv6 тоже не нужно ничего дополнительного. Добавьте
его в панели, записав адрес просто:

```
2001:db8::1
```

Скобки принимаются и отбрасываются — `[2001:db8::1]` и `2001:db8::1` это одна и та
же нода. Панель возвращает их там, где этого требует синтаксис, и не ставит там,
где не требует: ссылка получается как `vless://…@[2001:db8::1]:443?…`, профиль
wireguard — как `Endpoint = [2001:db8::1]:51820`, тогда как конфигурация clash или
sing-box и строка `remote` в OpenVPN несут голый адрес. То же касается **публичного
адреса** (адреса, публикуемого в ссылках, когда он отличается от того, к которому
подключается панель) и SSH-хоста автоматической установки.

Одного IPv6 не меняет: если у inbound'а включён TLS и SNI не задан, клиент
проверяет сертификат по адресу, а значит этот адрес должен быть в сертификате.
Перевыпустите сертификат ноды с адресом IPv6 в списке SAN — ровно так же, как
сделали бы с IPv4.

## Панель и нода на одном сервере

**Не рекомендуется.** Это работает, и ничто в Nexora этого не запрещает — но
сначала прочитайте, почему вам это, скорее всего, не нужно.

Друг другу они не мешают. Панель слушает 2095, нода — 62050; они ставятся в
`/opt/nexora-panel` и `/opt/nexora-node`, работают как отдельные сервисы systemd
и делят только корень каталогов состояния: `/var/opt/nexora/nexora.db` и
`/var/opt/nexora/bin/` принадлежат панели, `/var/opt/nexora/certs/` — ноде.

Чтобы так сделать, выполните однострочную команду установки на самом сервере
панели и привяжите управляющий API к loopback — панель ведь уже здесь:

```bash
curl -fsSL https://PANEL/install-node.sh | bash -s -- \
  --panel PANEL --token TOKEN --listen 127.0.0.1:62050
```

Затем добавьте ноду в панели с адресом `127.0.0.1`. Порт 62050 не выходит за
пределы машины, так что правило `ufw` выше можно вообще пропустить.

Для Docker в репозитории панели есть готовый стек ровно с такой схемой:
[`docker/panel-and-node`](https://github.com/nexora-vpn/panel/tree/main/docker/panel-and-node).

### Почему не рекомендуется

- **Это раскрывает адрес вашей панели.** IP ноды попадает в каждую
  подписочную ссылку и в каждый выданный клиентский конфиг. Совмещение означает,
  что любой пользователь — и любой, кто эти конфиги соберёт, — узнает, где живёт
  ваша панель. Если этот адрес затем отфильтруют или занесут в чёрный список за
  прокси-трафик, вы потеряете не одну ноду, а панель и все подписочные ссылки
  разом.
- **Одна машина — одна судьба.** Клиентский трафик рваный и ничем не ограничен:
  он съедает CPU, память, файловые дескрипторы и полосу. Нода под нагрузкой
  утянет панель за собой — а упавшая панель обрушит подписки пользователей
  *всех* остальных нод.
- **Это склеивает одноразовое с незаменимым.** Ноду предполагается выбросить и
  зарегистрировать заново; база панели — единственное во всём парке, что стоит
  бэкапить. На общем сервере переустановка ноды делается поверх этой базы.
- **Удаление — грабли.** `rm -rf /var/opt/nexora` из раздела «Удаление» ниже
  сотрёт базу панели. На общем сервере удаляйте только `/opt/nexora-node` и
  `/var/opt/nexora/certs`.
- **Ноду всё равно придётся оплатить.** Совмещённая нода считается в лимите нод
  вашей лицензии точно так же, как любая другая.

Для лаборатории, демо или небольшой односерверной установки — где вы принимаете,
что панель и прокси делят один адрес и одну судьбу, — это разумный выбор. Для
всего, что жалко потерять, дайте панели отдельный сервер.

## Ручная установка

Для сервера без выхода в интернет, хоста без systemd или панели, которой вы не
хотите разрешать исходящие запросы, — те же четыре шага вручную.

**1. Установите бинарник.**

```bash
ARCH=amd64   # или arm64, armv7, armv6, armv5, 386, s390x, riscv64
curl -fsSL -o /tmp/node.tar.gz \
  https://github.com/nexora-vpn/node/releases/latest/download/nexora-node-linux-${ARCH}.tar.gz
tar -C /tmp -xzf /tmp/node.tar.gz
mkdir -p /opt/nexora-node /var/opt/nexora/certs
install -m 0755 /tmp/nexora-node/nexora-node /opt/nexora-node/nexora-node
```

**2. Возьмите клиентский сертификат панели.** Скопируйте его со страницы
установки ноды в панели и сохраните как `/var/opt/nexora/certs/panel_ca.pem`. Это
публичный сертификат, а не секрет — нода, у которой он есть, всё равно ничего не
может сделать с панелью.

**3. Сгенерируйте собственный сертификат ноды.**

```bash
/opt/nexora-node/nexora-node gencerts -dir /var/opt/nexora/certs
```

**4. Настройте и запустите.**

```bash
cat > /opt/nexora-node/config.json <<'JSON'
{
  "listen": "[::]:62050",
  "cert_file": "/var/opt/nexora/certs/ssl_cert.pem",
  "key_file": "/var/opt/nexora/certs/ssl_key.pem",
  "client_ca_file": "/var/opt/nexora/certs/panel_ca.pem"
}
JSON

cp /tmp/nexora-node/nexora-node.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now nexora-node
```

Затем добавьте ноду в панели с адресом этого сервера и портом 62050. Панель
закрепит сертификат на первом соединении ровно так же, как после скриптовой
установки.

## Docker

```bash
git clone https://github.com/nexora-vpn/node
cd node
mkdir -p certs
cp /path/to/panel_ca.pem certs/
docker compose up -d
```

Compose-файл намеренно использует сеть хоста. Нода терминирует клиентский трафик
на портах своих inbound'ов, а те выбираются в панели уже потом — при bridged-сети
каждый новый inbound означал бы правку compose-файла и пересоздание контейнера.

## Обновление

Ноды обновляются из панели: откройте окно установки узла, перейдите на вкладку
**Автоматически (SSH)** и нажмите **Обновить**. Панель загрузит новый бинарник
(или подтянет новый образ), заменит работающий и перезапустит его. На самой ноде
набирать ничего не нужно.

Ручная команда тоже обновляет на месте — запустите её ещё раз на сервере, где
нода уже есть: она обнаружит существующую установку, сохранит `config.json` и
сертификаты и заменит только бинарник:

```bash
curl -fsSL https://PANEL/install-node.sh | bash -s -- --panel PANEL --token TOKEN
```

Либо замените бинарник сами и перезапустите:

```bash
systemctl stop nexora-node
install -m 0755 /tmp/nexora-node/nexora-node /opt/nexora-node/nexora-node
systemctl start nexora-node
```

Обновление не трогает сертификаты, поэтому закреплённый панелью отпечаток
по-прежнему сходится и нода возвращается без повторной регистрации.

В Docker: `docker compose pull && docker compose up -d`.

## Удаление

```bash
systemctl disable --now nexora-node
rm -f /etc/systemd/system/nexora-node.service
systemctl daemon-reload
rm -rf /opt/nexora-node /var/opt/nexora
```

Если панель установлена на этом же сервере, **не** удаляйте `/var/opt/nexora` —
там лежит её база. Удалите только `/var/opt/nexora/certs`.

Удалите ноду и в панели, иначе она продолжит считаться в вашей лицензии и висеть
как офлайн.

## Что где лежит

| Путь | Что это |
| --- | --- |
| `/opt/nexora-node/nexora-node` | бинарник |
| `/opt/nexora-node/config.json` | адрес прослушивания и пути к сертификатам — и больше ничего |
| `/var/opt/nexora/certs/ssl_cert.pem` | собственный серверный сертификат ноды |
| `/var/opt/nexora/certs/ssl_key.pem` | его закрытый ключ |
| `/var/opt/nexora/certs/panel_ca.pem` | клиентский сертификат панели — единственный принимаемый |
| `/etc/systemd/system/nexora-node.service` | unit службы |

Всё остальное — inbound'ы, outbound'ы, endpoint'ы, маршрутизация, пользователи —
приходит из панели и живёт в памяти. Больше на диске резервировать нечего.

## Диагностика

**Команда установки падает с `node binary not provisioned`.** У панели нет
бинарника для этой архитектуры. Подготовьте его на хосте панели, как показано
выше, и повторите команду со свежим токеном.

**Команда установки падает с `invalid token` или `token already used`.** Токены
установки ноды одноразовые и с ограниченным сроком. Сгенерируйте новый в панели и
скопируйте команду целиком заново.

**Нода работает, а панель показывает её офлайн.** Что-то между ними рвёт
соединение. Проверьте по порядку:

```bash
systemctl status nexora-node          # на ноде
journalctl -u nexora-node -n 50       # на ноде
nc -vz NODE_IP 62050                  # с сервера панели
nc -vz -6 2001:db8::1 62050           # …если панель приходит по IPv6
```

Обычная причина — правило файрвола, не включающее адрес панели; вторая по
частоте — security group облачного провайдера. Если нода доступна по IPv6,
проверьте, что правило файрвола именно v6 — правило v4 его не покрывает — и что
`ss -lnt | grep 62050` показывает ноду на `[::]`, а не на `0.0.0.0`: второе значит,
что IPv6 на хосте выключен и нода откатилась.

**Нода переустановлена, и панель её не принимает.** Переустановка создаёт новый
серверный сертификат, а панель всё ещё держит закреплённым старый. Удалите ноду в
панели и добавьте заново — отпечаток будет взят заново на следующем первом
соединении.
